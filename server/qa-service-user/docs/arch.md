## 2. 系统概述

### 业务背景
QA Service User 是医疗问答系统的核心用户管理服务，负责医生用户的信息管理、认证授权等功能。该服务为整个医疗问答平台提供基础的用户数据支持。

### 核心功能
- **医生用户管理**：医生信息的增删改查操作
- **用户认证**：医生用户的登录认证（规划中）
- **权限管理**：基于角色的访问控制（规划中）
- **跨域支持**：支持前后端分离架构的跨域访问
- **健康监控**：提供应用健康检查和监控指标

### 用户角色
- **医生用户**：使用系统的医务人员，可以管理个人信息
- **系统管理员**：管理医生用户账户和权限
- **前端应用**：通过RESTful API访问服务的Web或移动应用

## 3. 架构设计目标

### 高性能
- 支持高并发访问，接口响应时间 < 200ms
- 数据库查询优化，使用索引提升查询效率
- 支持连接池管理，提升数据库访问性能

### 高可用
- 服务可用性 ≥ 99.5%
- 支持健康检查和自动重启
- 容器化部署，快速恢复服务

### 可扩展性
- 无状态服务设计，支持水平扩展
- 模块化设计，新增业务模块影响范围小
- 数据库支持读写分离（规划中）

### 安全性
- 密码加密存储
- 支持CORS跨域配置
- SQL注入防护（使用JPA参数化查询）
- 敏感信息不输出到响应DTO

### 可维护性
- 分层架构清晰，职责明确
- 代码规范统一，遵循编码规范
- 完善的文档体系（API、数据模型、架构文档）

### 5.2 核心模块职责
| 模块 | 职责 | 关键类/包 |
|------|------|----------|
| **控制器层** | 接收HTTP请求，参数校验，调用服务层，返回响应 | `DoctorUserController` |
| **服务层** | 业务逻辑处理，事务管理，数据转换 | `DoctorUserService`, `DoctorUserServiceImpl` |
| **数据访问层** | 数据库CRUD操作，自定义查询 | `DoctorUserRepository` |
| **实体层** | 数据库表映射，定义数据结构 | `DoctorUser` |
| **DTO层** | 数据传输对象，隔离实体与外部接口 | `DoctorUserRequest`, `DoctorUserResponse` |
| **配置层** | 应用配置，CORS配置，数据库配置 | `CorsConfig` |

### 5.3 模块交互流程

```

    ↓
```

### 6.2 数据库设计

#### 主表：doctor_user
| 字段名 | 类型 | 约束 | 说明 |
|--------|------|------|------|
| id | VARCHAR(20) | PRIMARY KEY | 医生用户唯一标识 |
| username | VARCHAR(50) | NOT NULL, UNIQUE | 登录用户名 |
| password | VARCHAR(255) | NOT NULL | 登录密码（加密存储） |
| name | VARCHAR(50) | NOT NULL | 医生真实姓名 |
| title | VARCHAR(30) | - | 职称 |
| department | VARCHAR(30) | - | 所属科室 |
| avatar | TEXT | - | 头像URL |
| experience | VARCHAR(50) | - | 从业经验 |
| is_active | BOOLEAN | NOT NULL, DEFAULT TRUE | 账户激活状态 |

#### 关联表：doctor_specialties
| 字段名 | 类型 | 约束 | 说明 |
|--------|------|------|------|
| doctor_id | VARCHAR(20) | FOREIGN KEY | 关联医生ID |
| specialty | VARCHAR(255) | - | 专长项 |

### 6.3 数据关系
```
doctor_user (1) ←→ (N) doctor_specialties
    ↓
一个医生可以有多个专长
采用一对多关系，级联删除
```

### 6.4 数据治理
- **数据备份策略**：定期备份doctor_user和doctor_specialties表
- **数据归档**：暂无归档需求，未来可考虑归档不活跃医生数据
- **敏感数据加密**：password字段使用加密存储（建议使用BCrypt）
- **数据验证**：
  - username全局唯一
  - password最小长度要求
  - name必填

## 8. 安全架构

### 8.1 认证与授权
- **认证方式**：暂未实现，规划使用JWT进行无状态认证
- **权限控制**：暂未实现，规划使用RBAC模型
- **会话管理**：无状态服务，不使用Session

### 8.2 数据安全
- **传输加密**：建议生产环境使用HTTPS/TLS 1.2+
- **存储加密**：
  - password字段必须加密存储
  - 建议使用BCrypt加密算法
- **脱敏策略**：
  - 响应DTO中不返回password字段
  - 日志输出时脱敏敏感字段

### 8.3 接口安全
- **CORS配置**：
  - 允许所有源（开发环境）
  - 生产环境建议限制具体域名
  - 允许的方法：GET, POST, PUT, DELETE, OPTIONS
  
- **SQL注入防护**：
  - 使用JPA参数化查询
  - 禁止字符串拼接SQL
  
- **XSS防护**：
  - 对用户输入进行校验和过滤
  - 前端输出时进行转义

### 8.4 网络安全（生产环境建议）
- 配置防火墙规则，限制访问端口
- 使用VPC网络隔离
- 定期进行漏洞扫描

## 11. 关键设计决策与权衡

### 11.1 为什么选择Spring Boot？
- **快速开发**：自动配置、开箱即用
- **生态完善**：丰富的Starter依赖
- **微服务友好**：易于拆分为微服务架构
- **社区活跃**：问题易解决，文档完善

### 11.2 为什么选择JPA而不是MyBatis？
- **开发效率**：简单CRUD无需手写SQL
- **对象化**：面向对象的数据访问方式
- **跨数据库**：易于切换数据库类型
- **缓存支持**：一级缓存、二级缓存

### 11.3 为什么使用DTO而不是直接返回Entity？
- **解耦**：隔离实体层与外部接口
- **安全**：控制返回的字段，避免暴露敏感信息（如password）
- **灵活**：可以组合多个Entity的字段
- **版本兼容**：接口变更时影响范围小

### 11.4 为什么使用Docker部署？
- **环境一致性**：开发、测试、生产环境一致
- **快速部署**：容器化部署，启动快速
- **资源隔离**：容器间资源隔离，互不影响
- **易于扩展**：容器编排工具支持弹性伸缩

### 12.2 潜在风险

  - **解决方案**：部署多实例，使用负载均衡
  
- **数据一致性**：未来引入缓存后可能出现数据一致性问题
  - **解决方案**：使用缓存失效策略或分布式锁
  
- **性能瓶颈**：数据库可能成为性能瓶颈
  - **解决方案**：添加缓存层、数据库读写分离、分库分表

### 12.3 优化方向
- **短期优化**（1-3个月）：

- **中期优化**（3-6个月）：

  - 引入Redis缓存层
  - 数据库读写分离
